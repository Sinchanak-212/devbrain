# DevBrain — przekazanie rozwoju do nowej sesji

Stan na 7 listopada 2026. Ten plik przekazuje ustalenia i stan prac; nie jest
kopią całej rozmowy ani bazą użytkownika. Rozpakuj dołączony pakiet i zacznij
od tego pliku, devbrain/README.md oraz dokumentacji w devbrain/docs/.

## Cel użytkownika i ustalone decyzje

DevBrain to lokalne środowisko programistyczne ze wspólną, trwałą pamięcią
dla agentów. Jedna komenda devbrain, uruchomiona z dowolnego katalogu, otwiera
rejestr projektów oraz terminalowe panele wybranych klientów, pamięci i grafu.
Główny interfejs ma być TUI w terminalu/tmuxie, a nie aplikacją internetową.
Natywne Codex CLI i Claude Code mają zachować własne interfejsy i uprawnienia.

Pamięć rozdziela projekty, źródła, fakty, decyzje, plany, zadania, zależności,
statusy, checkpointy, rewizje oraz dowody testów/review. Ma odtwarzać stan
bez poprzedniej rozmowy, korzystając z wyszukiwania i powiązań grafowych.
Nie deklarować usunięcia fizycznego limitu kontekstu ani bezbłędnej pamięci:
system ma jawnie zgłaszać brak źródeł, nieaktualność i niepełny stan.

Wybrana baza to ArcadeDB, nie SQLite ani SurrealDB. Użytkownik wybrał najpierw
lokalny kokpit jednej osoby, z własnymi połączeniami API. Własny silnik agenta
API jest częścią DevBrain; nie zastępować go OpenCode bez nowej decyzji.
Profile mają obsługiwać m.in. Ollamę, natywnego Codexa i Claude'a, bezpośrednie
API oraz GitHub Copilot. Rozliczenia i logowania tych usług są oddzielne.

## Aktualny stan wydania

Źródła i najnowszy przygotowany pakiet: 0.7.1. Nie zakładać, że użytkownik
już zainstalował tę poprawkę — w poprzedniej sesji dostał link i instrukcję.

Gotowe funkcje obejmują wspólną pamięć i protokół wznowienia, plany/zadania
z dowodami, projektowe snapshoty .memory/devbrain/, kokpit TUI tmux/Textual,
inspektor, graf, profile klientów i własnego agenta API. Połączenia obejmują
OpenAI Responses, Anthropic Messages, API zgodne z OpenAI, lokalną Ollamę
i osobny adapter oficjalnego Python SDK GitHub Copilot.

Wersje formatów: schema bazy 4, profile 2, administracyjny backup 5,
przenośna pamięć projektu 1. ArcadeDB jest przypięte do 26.11.1.

Ostatnie zlecenie użytkownika dotyczyło awarii grafu i zbyt płaskiego wyglądu:
TypeError: Style.from_rich_style() missing 1 required positional argument:
'rich_style'. Poprawka 0.7.1 dodaje graph_raster.py: rzeczywiste współrzędne
XYZ, perspektywę, cieniowane sfery ASCII, proporcje komórki terminala, wspólny
bufor głębokości dla węzłów i relacji oraz ciągły obrót. Inspiracją jest
klasyczny ASCII donut; graf nadal pokazuje rzeczywiste dane, nie demo donuta.
Limit sceny to 300 węzłów i 800 relacji, maksymalnie 10 odświeżeń/s.

TerminalGraph w terminal_graph.py przekazuje kolory przez natywne Strip
Textuala i omija konwersję Rich do Content. Testy wymuszają dokładny zgłoszony
TypeError i sprawdzają rzeczywisty compositor. Pierwotna awaria nie odtworzyła
się na przypiętym Textual 8.2.8; dokładna przyczyna w pierwotnym runtime nie
została ustalona. Nie przypisywać jej arbitralnie innej wersji zależności.

## Dowody i granice weryfikacji

evidence/devbrain-0.7.1-validation.json wiąże wyniki z hashami pakietów.
Przeszło 125 unikalnych testów: ukierunkowana regresja terminala, grafu,
inspektora, integracji API oraz zabezpieczeń aktualizatora. Fazy mają nakładanie:
110 testów terminala, 25 finalnych testów grafu i 5 guardów, nie 140 unikalnych.
Przeszła instalacja dokładnego aktualizatora 0.7.0 -> 0.7.1 w izolowanym
środowisku: zachowane źródła pamięci, profile, klucze testowe, modele,
uprawnienia, kopie zapasowe i idempotencja. Sprawdzono rzeczywisty painter
z niepustym grafem po instalacji oraz pięć paneli w prawdziwym tmuxie.

Przechwycono 50 różnych, poprawnych klatek prawdziwego GraphApp w tmux 3.4,
przy rozmiarach 120x40 i 70x25. Dane pochodziły z produkcyjnego Inspector.graph
na izolowanym ArcadeDB; transport brokera był kontrolowany i tylko do odczytu.
Dołączono GIF i raport pochodzenia. Obejrzano cieniowanie i zasłanianie brył.

To nie był ponowny pełny test całego backendu z 0.7.0. Nie wykonywano płatnej
inferencji modeli ani testu na fizycznym Windows/WSL użytkownika. Testy modelu
w scenariuszach automatycznych używają kontrolowanych adapterów. Samo otwarcie
kokpitu nie ma uruchamiać płatnych zapytań ani pobierać runtime Copilota.

## Co dalej

Użytkownik przenosi pracę do nowej rozmowy. Nie zlecił jeszcze kolejnej funkcji.
Nie restartować ukończonych etapów pamięci, TUI i profili API.
Pomysł na przyszłość: konfigurowalny mały koordynator, który sam kieruje
planowanie, implementację i review do odpowiednich klientów/modeli.
Nie przedstawiać takiego koordynatora jako już ukończonej funkcji.
Nowy cel rozwoju należy uzgodnić z użytkownikiem po odtworzeniu stanu.

DEVBRAIN_TEST_TMUX binarkę tmuxa. Nie zatrzymuj współdzielonego silnika ani
nie usuwaj baz obcych procesów; izoluj własne fixture'y.

## Pamięć z komputera użytkownika

Ten pakiet przenosi kod i stan rozwoju, nie prywatną bazę na komputerze.
Jeśli użytkownik chce osobno przenieść pamięć konkretnego projektu na inny
komputer, istnieje devbrain memory snapshot PROJEKT, a potem jawny import
.memory/devbrain/ z --root NOWY_KATALOG. Sprawdź README i MEMORY_CONTRACTS.
Nie używaj restore całego magazynu do importu jednego projektu. Nie przenoś
aktywnych sesji, ACK, kluczy ani uprawnień. Historyczne testy po imporcie
pozostają historyczne i nie stają się lokalnym fresh bez rzeczywistego runu.
W nowej sesji agenta uruchomionej przez DevBrain obowiązuje normalny odczyt
resume_context i dokładny ACK; partial blokuje zapisy. Nie omijaj tego.
